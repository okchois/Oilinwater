## 프롬프트

이 프로젝트의 펌웨어 업데이트 방식을 **두텍 표준 RS-485 자체 부트로더**로 맞춰 주세요. 기준은 HMT500(260313) 오일 수분 트랜스미터 프로젝트(GitHub `okchois/Oilinwater`, 브랜치 `claude/oil-moisture-transmitter-shji8x`)에서 확정한 방식입니다. 그 저장소를 읽을 수 있으면 다음 파일을 먼저 읽으세요 (읽을 수 없으면 아래 요약만으로 진행):
- `docs/rs485-bootloader-design.md` (설계 v0.2: 메모리 맵, 부팅 흐름, 이미지 형식 .oiw, 부트로더 Modbus 레지스터, 업데이트 순서, 안전 설계)
- `firmware/bootloader/bl_core.[ch]`, `bl_port.h` (MCU 비의존 부트로더 코어), `firmware/common/` (CRC, 이미지 헤더)
- `tools/fwupdate.py` (PC 도구), `tests/test_bootloader.py` (시뮬레이터 시험 7종)
- `docs/hw/final-review-260313A.md` F절 (몰딩 후 업데이트 검토)

### 1. 확정된 방침 (모든 제품 공통)
1. **자체 상주 부트로더**를 플래시 앞 32 KB에 둔다. 제품 동작 프로그램(앱)과 분리하고, 부트로더는 현장에서 갱신하지 않는다.
2. **ST 내장(ROM) 부트로더는 현장 업데이트에 쓰지 않는다.** 이유: ROM 부트로더는 RS-485 DE 핀을 켜지 못해 응답할 수 없고, 몰딩·밀폐 후 BOOT0 진입이 불가능하며, 읽기 보호(RDP 1)와 충돌해 풀면 교정값까지 지워진다.
3. 업데이트는 **제품의 평소 RS-485 선과 같은 Modbus 슬레이브 주소**로, 표준 함수(FC03/06/16)만 써서 한다. 버스를 다른 기기와 공유한 채 업데이트할 수 있고, PLC·게이트웨이에서도 구현 가능하다.
4. 최초 기록은 조립(몰딩·밀폐) 전 벤치에서 **SWD로 "부트로더 + 앱"을 한 파일로** 기록한다.
5. **교정값·시리얼·설정은 앱 영역 밖**의 별도 페이지에 두어 업데이트로 지워지지 않게 한다.

### 2. 하드웨어 필수 조건 (회로 확인·수정)
- RS-485 트랜시버 DE(와 /RE)는 MCU USART의 **하드웨어 DE 기능 핀**으로 제어한다 (STM32 `DEM`, USART2이면 보통 PA1 — 칩별 AF 번호는 데이터시트로 확인).
- **DE 선에 10 kΩ 풀다운** (리셋·부팅·부트로더→앱 점프 중 송신기 꺼짐, 수신 켜짐). 절연 트랜시버를 쓰면 MCU 쪽 DE 선에 둔다.
- SWD(SWDIO, SWCLK, NRST, GND, VCC) 접근점은 조립 전까지 사용할 수 있게 둔다 (예: Tag-Connect).
- 크리스털이 없으면 HSI 정확도(온도 범위 전체)와 USART 수신 허용 오차를 데이터시트·레퍼런스 매뉴얼로 확인하고, 부족하면 HSE 또는 32.768 kHz 자리를 DNP로 둔다.
- 전원이 제품 커넥터로 들어오는지 확인한다 (전원 재투입 = 복구 창 진입 수단).

### 3. 펌웨어 필수 조건
1. **원자적 유효화:** 앱 헤더(magic, 버전, 크기, CRC-32, HW ID)를 **마지막에** 기록한다. 중간에 정전·통신 끊김이면 헤더가 없어 다음 부팅에 부트로더에 머문다.
2. **HW ID 확인:** 다른 모델·보드 리비전용 이미지를 거부한다 (제품마다 고유 HW ID 배정).
3. **전원 투입 복구 창:** 전원 켠 뒤 약 1 s 동안 고정 설정(19200 8E1)과 저장 설정으로 듣고, **매직 요청**(FC06 0x1000 = 0xB007 또는 시리얼 번호가 든 전용 요청)에만 반응한다. 일반 폴링에는 응답하지 않는다.
4. **부팅 확인 카운터:** 부트로더가 점프 전 백업 레지스터 카운터를 올리고, 앱은 정상 동작 확인 후(예: Modbus 30 s) 0으로 지운다. 확인 안 된 부팅 3회 또는 IWDG 리셋 반복이면 부트로더에 머문다.
5. **하드웨어 워치독:** 옵션 바이트로 리셋 직후 시작 (STM32 IWDG_SW = 0). 부트로더는 플래시 소거 사이에도 갱신한다.
6. **앱 → 부트로더 진입:** 앱은 홀딩 레지스터 0x1000에 0xB007을 받으면 먼저 정상 응답을 보내고, 송신 완료 후 백업 레지스터에 플래그를 쓰고 리셋한다.
7. **업데이트 중 출력:** 아날로그 출력(4–20 mA 등)이 있으면 들어가기 전 설정값(NAMUR ≤ 3.6 mA 고장 전류 또는 마지막 값 유지)으로 두고, 부트로더에도 같은 값을 거는 최소 드라이버를 넣는다.
8. **옵션 바이트:** 플래시 부팅 고정(BOOT0 핀 무시), NRST = 리셋 입력, BOR 높은 문턱, WRP = 부트로더 32 KB, **RDP 레벨 1** (IAP 가능). **RDP 레벨 2 금지.** 앱은 옵션 바이트를 쓰지 않는다.
9. 부트로더 Modbus 레지스터 맵·업데이트 순서(BEGIN → DATA × N → FINISH → RUN)·이미지 형식(.oiw)은 기준 설계와 **같게** 해서 PC 도구(`fwupdate.py`, 이후 GUI 앱)를 모든 제품이 공유한다. 제품별 차이는 HW ID와 메모리 맵뿐이다.

### 4. MCU별로 맞출 것 (이 프로젝트의 MCU를 먼저 확인)
- 기준 프로젝트: **STM32G0B1CCT3** (256 KB, 이중 뱅크 2 × 128 KB, 2 KB 페이지, 64비트 기록). 앱 슬롯에 바로 기록하는 방식 (부트로더 32 KB | 앱 208 KB | 설정 8 KB | 교정 8 KB).
- 이 프로젝트의 MCU가 다르면 (예: **STM32G491CET3**, 512 KB 단일 뱅크) 레퍼런스 매뉴얼(G4 = RM0440)로 페이지 크기·기록 단위·뱅크 구조·WRP 단위·옵션 바이트 이름을 확인해 `bl_port.h`의 플래시 함수 3개와 메모리 맵만 새로 만든다.
- 플래시가 넉넉하면 **받기 영역(staging) 방식**을 써도 된다: 새 이미지를 빈 영역에 받는 동안 앱은 계속 동작 → CRC·HW ID 확인 → 부트로더가 앱 영역으로 복사 (복사 중 정전이어도 원본이 남아 다시 복사). 이 경우에도 3의 조건(헤더 마지막, 복구 창, 카운터, 워치독)은 모두 지킨다. 프로토콜과 이미지 형식은 같게 유지한다.
- 칩 대체품(예: G491 ↔ G474)이 있으면 부트로더가 칩 ID(DBGMCU_IDCODE)와 플래시 구조를 읽어 맞추거나, 옵션 바이트로 같은 구조로 쓰게 한다.

### 5. 할 일 (순서대로 진행하고 각 단계 결과를 보고)
1. 현재 회로·문서·펌웨어에서 위 1–3과 **다른 점을 표로 정리** (항목, 현재, 필요한 변경, 근거 문서).
2. 회로 변경이 필요하면 회로도 생성기·문서에 반영하고 검사(테스트·넷리스트)를 통과시킨다.
3. 설계 문서(이 프로젝트용 부트로더 설계서)를 만들거나 갱신: 메모리 맵, HW ID, 옵션 바이트 값, 복구 창·카운터·워치독, 출력 안전값.
4. 기준 부트로더 코어(`bl_core`)와 PC 도구를 가져와(가능하면 공용 모듈로) 이 MCU의 포트 계층과 링커 스크립트를 만든다. 호스트 시뮬레이터 시험(전체 업데이트, HW ID 거부, 재전송, CRC 손상, 전원 차단 복구, 주소 필터)을 통과시킨다.
5. 실제 보드 시험 항목(업데이트 중 전원·통신 차단, 손상 이미지, 멈추는 앱, 온도 끝단 통신)을 시험 계획에 넣는다.
6. 결정 기록에 "펌웨어 업데이트 = 두텍 표준 자체 부트로더 (Oilinwater 결정 #31 기준)"를 남긴다.
